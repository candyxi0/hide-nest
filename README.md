# Nest Core

面向 AI 的长期记忆与连续性底座。

Nest 希望让交互中形成的经历、事实与理解，在未来相关情境中继续发挥作用，并能随着新的信息被补充、修正和重新理解。

项目起点来自长期使用 AI 的实际体验：窗口会结束，上下文会压缩，模型和 Agent 也会更换。聊天记录虽然保留下来了，但其中发生过的变化，往往很难自然地进入下一次判断。

Nest Core 围绕这个问题，建设一套与具体业务和角色解耦的长期记忆系统。

> 当前处于 V2 开发阶段。V1 已通过 MCP 提供记忆服务；V2 正在实现自动摄取、记忆演变与 Agent 检索，端到端连续性效果仍待验证。

## 一个具体例子

某个项目最初将设备超时设置为 90 秒，后来因为现场反馈调整为 30 秒，并讨论过未来回滚的可能性。

后续 Agent 再处理这个项目时，需要分清：

- 当前采用的配置是什么；
- 哪些值已经成为历史；
- 当时为什么修改；
- “考虑回滚”是否已经执行；
- 这些说法分别来自哪些记录。

Nest 希望保存并提供这样的材料，使当前模型能够结合当下情况作出判断。

相同机制也可以用于协作偏好、项目经验或关系中的理解。例如“高压力时可能先需要喘息空间”，应当保留适用条件和形成依据，并允许后续经历改变它。

## 从 V1 到 V2

V1 通过 MCP 提供记忆写入与检索能力，实际试用暴露出几个问题：

- 依赖手动触发摄取，容易积压尚未整理的材料；
- 主模型即使拥有工具，也不一定主动调用；
- 固定向量相似度阈值难以同时控制漏查和误召回；
- 单条摘要难以表达理解的条件、变化过程和相互关系。

V2 因此将重点放在自动形成、版本演变和情境检索上。

## 核心设计

### 记忆能够追溯到证据

系统区分来源材料、必要证据和长期记忆：

- **SourceAnchor**：定位原始来源中的具体位置；
- **Evidence**：保存被长期内容引用的必要、有边界的文本证据；
- **Memory**：基于材料形成的长期内容。

Core 保留证据与来源定位，原始文件和完整聊天记录由来源系统管理。

长期内容分为四类：

| 类型            | 含义                 |
| ------------- | ------------------ |
| Event         | 整理后的经历，描述发生了什么     |
| Claim         | 带主体与适用范围的事实主张或状态陈述 |
| Quote         | 措辞本身值得保留的原话        |
| Understanding | 基于经历形成、带条件且可以修正的理解 |

类型表达内容含义。它们之间不存在从“低级记忆”晋升为“高级记忆”的固定阶梯。

### 保留当前理解，也保留变化来路

Memory 使用稳定身份组织不可变的 revision，由 current 指向当前采纳版本。

V2 提供三种规范变化：

- **CREATE**：形成新的长期记录；
- **REVISE**：在同一记录下形成新版本；
- **SUPERSEDE**：由新记录接替旧记录，保留显式接替关系。

支持与反例关系绑定具体版本。旧依据发生变化时，可以沿关系追查它对已有理解的影响。

Understanding 是供当前模型参考的解释，保留条件、视角和不确定性；它不承担强制行为规则或角色设定的职责。

### 模型负责语义判断，Core 负责规范提交

V2 将认知处理与数据一致性分开。

摄取 Agent 判断哪些内容值得保留、已有记忆是否需要修订，并提交结构化变更。Core 核验来源、引用、版本和幂等条件，在事务中原子提交记忆、证据与关系。

普通形成和可逆修订自动进行。用户按需查看结构、追溯依据和纠正内容，无需逐条审批。

### 检索可以继续追查

V2 检索 Agent 根据当前情境组织查询，寻找候选，按需读取当前版本、历史版本、关系与原始证据，再判断材料是否充分。

返回内容包含相关材料、适用条件、引用和未解决的缺口。检索 Agent 只有读取权限，当前主模型决定如何使用这些材料。

同一会话中刚形成或已经交付的内容，通过来源范围与版本排除信息避免重复召回；会话管理和上下文压缩由上层宿主负责。

## V2 目标架构

系统主要分为三部分：

| 部分                   | 职责                         |
| -------------------- | -------------------------- |
| 场景应用与 Agent Adapter  | 管理具体业务、角色设定、当前会话及来源接入      |
| Java Core            | 管理来源进度、任务、证据、记忆、版本、关系和规范读写 |
| 可插拔 Cognitive Worker | 承载摄取、检索及派生索引处理             |

Cognitive Worker 首选 Python 与 LlamaIndex AgentWorkflow，底层模型可替换。

**摄取 Agent**

读取有边界的来源材料，检索同实例中的既有记忆，决定新增、修订、接替或不产生长期变化，再由 Core 校验和提交。

**检索 Agent**

根据当前情境生成查询，使用派生索引寻找候选引用，经 Core 核验后读取正式内容，并按需继续追查。

**派生索引**

用于提高检索效率，可以异步更新、重放和重建。长期内容的正式版本与状态由 Core 管理，索引不承担权威存储职责。

一个连续性世界对应一个逻辑 Core 实例。同一世界可以连接不同窗口、模型或 Agent，不同实例的数据不自动共享。

## 如何判断连续性是否成立

Nest 的最终验证需要超出“数据已保存”和“检索命中”。

我们希望观察到：

1. 新经历形成了有来源、有条件的长期内容；
2. 后续相关情境能够取回这次变化及其依据；
3. 换窗口、模型或 Agent 后，仍能区分当前状态、历史和计划；
4. 新反馈能够再次修正旧理解；
5. 这些材料确实帮助后续判断，而没有把模型锁进固定回应。

工作场景与陪伴场景都会纳入评测。模型的语言风格相似、角色资料加载成功，不单独作为 Core 连续性成立的证据。

## 开发与验证

需要 JDK 25。数据库集成测试还需要可用的 Docker 环境，以运行 Testcontainers PostgreSQL 容器。

在 Windows 仓库根目录运行：
```powershell
# 校验内部合同
.\mvnw.cmd -pl modules/contracts -am test

# 运行 V2 数据库模块及其依赖测试
.\mvnw.cmd -pl modules/database-adapter-v2 -am test
```

Linux / macOS 使用 `./mvnw`。

这些命令用于开发验证。V2 的完整部署入口将在端到端接线完成后补充。

## AI 协同研发

Nest 同时是一项长期 AI 协同研发实践。

项目负责人承担真实问题定义、产品含义和关键方案取舍，与 AI 共同推演架构、数据流和状态转换。实施工作按范围与验收标准拆成工单，由 Coding Agent 执行，再根据代码、测试和回执复核、整改与提交。

实践过程中逐步形成了几项工作习惯：

- 根据任务难度、模型能力和成本安排分工；
- 在上下文交接时记录已确认决定、未决问题及实现状态；
- 允许施工方修复范围内的普通编码问题；
- 将影响产品方向或架构边界的问题带回共同设计；
- 将协作经验沉淀为可复用的共创 Skill。

AI 参与设计、编码和验证的过程会明确保留。架构方案、代码实现、测试结果和真实使用效果分别记录，便于继续检查和演进。
